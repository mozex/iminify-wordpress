# Iminify Image Optimizer

The WordPress plugin for Iminify (https://www.iminify.com), an image optimization service. Its wordpress.org slug, main file and text domain are `iminify-image-optimizer`.

## The plugin is thin on purpose

The service decides everything it can: a site's settings, which outputs are worth keeping, every limit and count, the bulk estimate, the status and upgrade messages. The plugin does only what has to run inside WordPress: catch uploads, edits and deletions, send an attachment's image, write back what the service returns, keep and restore backups, print `<picture>` markup for copies that exist, keep its own per-attachment state, and show what the service says. A rule that could run on the service goes there, because code in a public plugin can be read and changed by anyone who installs it. Every number the plugin shows comes from the service's answers, never typed into its copy.

## Rules, each with its reason

- **PHP 7.4 syntax.** WordPress runs on PHP 7.4 and later, and about one site in seven is still on 7.4. So no union types, `match`, enums, `readonly`, constructor promotion, named arguments, the nullsafe operator, `mixed` or a `static` return type. PHPCompatibilityWP (in `composer lint`) holds the code to it. WordPress 5.9 and later polyfill `str_contains()`, `str_starts_with()` and `str_ends_with()`.
- **WordPress 6.9 and later**, the floor of the bundled Action Scheduler, which follows WordPress's latest release minus two.
- **WordPress's coding standards** (WPCS 3, `WordPress-Extra`): the directory's reviewers and its automated release scan read code against them. Run `composer lint`; `vendor/bin/phpcbf` fixes what it can.
- **Prefixes everywhere:** `iminify_` for functions, options, hooks, transients and post meta, `IMINIFY_` for constants, the namespace `Iminify\WordPress`, and the literal text domain `iminify-image-optimizer` in every translation call. A WordPress site shares one global scope with every other plugin.
- **Files:** classes live in `includes/` under WordPress's file names (`Key_Store` in `includes/class-key-store.php`, `Api\Client` in `includes/api/class-client.php`), which `includes/class-autoloader.php` maps. Every PHP file starts with the `ABSPATH` guard.
- **No runtime libraries but Action Scheduler.** Two plugins that bundle different versions of one library break each other on the same site. Action Scheduler is the exception by design: it is loaded from the main file before `plugins_loaded`, never prefixed, and the newest copy on a site runs.
- **Every call to the service goes through `Api\Client`** on WordPress's HTTP functions, with TLS verified and no redirect followed. The site key is stored sealed (`Key_Store`), and is never printed, never sent to a browser, never put in a REST answer or a script.
- **Nothing reaches the service before the site is connected** (directory guideline 7): no call on activation, no telemetry, no remote assets.
- **Nothing that runs locally is locked by plan** (directory guideline 5): restore, serving WebP and AVIF copies that exist, the bulk screens, WP-CLI and backups keep working on any plan, with the day's images spent, or disconnected. Only the service refuses work.
- **Notices only on the plugin's own screens**, plus at most one dismissible notice elsewhere; no admin bar item and nothing on the front end by default but the `<picture>` markup and the few lines `Compat\Woocommerce` adds to WooCommerce's variation script (guidelines 10 and 11). Reading whole pages (`Delivery\Buffer`) and writing rules into the site's `.htaccess` (`Delivery\Rules`) are settings the person turns on.
- **Files the plugin writes go under the uploads folder, or over the images in the folders someone chose** (`Folders`), never into its own folder, which every update replaces. The one exception is its marked block in the site's `.htaccess` (`Delivery\Rules`). Backups live under the uploads folder in `Media\Paths::BACKUP_FOLDERS`: the library's in `iminify-backup/`, the other folders' in `iminify-backup-folders/` at their path in `wp-content`, since a path in the uploads folder can be anything and no name inside `iminify-backup/` is safe from an attachment's.
- **Optimizing runs in the background and never waits.** An upload, an edit or regenerated sizes only queues the attachment (`Media\Hooks`), since an upload request is already busy making sizes. `Media\Optimizer`'s Action Scheduler actions open a group, send the original and check back later: a `Retry-After`, a group still being made or an outage becomes the next run's time, never a `sleep()`, and a spent day holds no run at all (below).
- **An attachment's record (`Media\Records`, the `_iminify` post meta), and a file's row in `Folders\Table` for an image in another folder, is the only proof a file is the plugin's own.** It names every file the plugin wrote over, with the bytes it wrote, and every WebP or AVIF copy with its origin. The original comes only from `Media\Originals::find()`, which never answers a file the plugin wrote, only its backup, so no image is compressed twice. Delete only copies whose recorded origin is the plugin's.
- **An image never passes through PHP's memory whole.** A source goes out as a file cURL reads from the disk (`Api\Upload`: the request carries no body and `Upload::ARGUMENT`, and the `http_api_curl` action hands cURL a `CURLFile`), and a zip entry is copied into its temporary file a piece at a time (`Zip::extract()`), so an original as large as the plan takes goes through on a 128 MB limit. Where WordPress can't send over cURL the body is built in memory, and `Upload::max_bytes()` caps the source `Originals::find()` may answer, so a larger original gives way to WordPress's `-scaled` copy. The test stub sees `Upload::ARGUMENT`, never the bytes.
- **Attachments that share their files have one holder** (`Media\Shared`): WPML and Polylang translate an image by adding attachments that name the same `_wp_attached_file`. Only the holder (the one whose record has work on the files, else the lowest id) is ever sent; the others read `shared` in `Optimizer::why_not()`, `Originals::find()` answers nothing for them, `Hooks` queues the holder for any change to their files, and deleting one deletes nothing the files still need, the holder's record moving to the next (`Shared::leaves_files()`). A new path that sends, restores or deletes an image's files goes through the holder too. Post meta has no index on its value, so who names a file is kept for the request (`Shared::others()`), dropped when an attachment's file changes, before each Action Scheduler action and on each WP-CLI look; a path that writes or deletes files asks afresh (`$fresh`, as `Optimizer::optimize()`, `Hooks` and `Shared::leaves_files()` do), so no kept answer can send a translation's files. Names match byte for byte, since the column's collation ignores case. A screen or run that asks about a page of images primes them in one query first (`Shared::prime()`, which `the_posts` does for the media screens' queries). A file another attachment's record keeps a backup of is never an original (`Originals::find()`), since it is that one's output, as when a translation plugin leaves a translation on its holder's old file after an edit. `wpml-config.xml` keeps every `Records::ALL_META` key out of WPML's and Polylang's copies, which `SharedTest` pins. Each of the others keeps the holder's id in its record (`holder`, written by `Shared::point()`) wherever the holder is already known: the holder's finish (`Optimizer::finish()`, asked afresh), a set-aside (`Optimizer::skip()`, the bulk run's too), `Hooks::changed()`, `Shared::leaves_files()`, and an attachment coming to name a file with a copy or a backup of the plugin's (`Shared::file_changed()`, which asks nothing of a new upload's name, since it has neither). `Picture::source()` follows it one step, only while both name the same file byte for byte, so a pointer left behind serves nothing; it is no work (`holds_work()` ignores it), and a page reads its translations' holders in one go (`Picture::prime()`, from `prime_content()` before core's `wp_filter_content_tags` and from the buffer).
- **A regeneration's sizes name no bytes** (`Optimizer::regenerated()`): when WordPress made sizes again from a main file the plugin wrote (Regenerate Thumbnails, `wp media regenerate`), they are copies of a copy, so their group declares them without bytes and the service's files, made from the backup, replace them.
- **The background queue's requests to the site itself carry its basic-auth password** (`Loopback`, on `cron_request` and Action Scheduler's async request): `IMINIFY_AUTH_USER` and `IMINIFY_AUTH_PASSWORD` from wp-config.php, else the credentials the request making them came with, outside REST and XML-RPC. Nothing is stored, and calls to the service never carry them.
- **Other folders go through their own pipeline beside the library's** (`Folders\Optimizer`, `Folders\Restorer`, `Folders\Scanner`), one group per file with no sizes and `keep_dimensions`, which Iminify reads only from a site key so a theme's image keeps its width and height whatever the site's maximum width and size limit. What a refusal means is one decision for both (`Media\Refusal::decide()`); a change to it goes there, never into one pipeline. `Media\Writer::put()` writes either's files under its root.
- **A file in another folder is read or written only through `Folders::guard()`**, which asks again of the file's real path what `Folders::check()` asked of the folder: inside a chosen folder in `wp-content`, outside the uploads folder, the plugin's own folder, the tool folders (`Folders::TOOL_FOLDERS`) and hidden or dependency folders, and no link on the way. A row is data anyone with the database could have written, so a path from it is never trusted on its own; a copy is deleted only beside its file.
- **The folders' rows outlive the list.** Taking a folder off the list keeps its rows, and a file a scan no longer finds reads `missing`, since each row is the proof of what the plugin wrote; a scan finding it again puts it back where it stood. The table is made with the first folder (`Table::create()`), never on a site that chooses none, on `base_prefix`, and goes only when uninstall deletes both the copies and the backups. On a network only the main site lists folders (`Folders::available()`), since every site shares `wp-content`.
- **A scan walks under a time budget and goes on where it stopped** (`Scanner::step()`, its queue of folders kept in an option, at least one folder a step), since a folder can hold more files than a request can look at; a run over the folders refuses to start while one is under way. A file whose bytes are no longer what the plugin wrote or last saw has changed: it reads not optimized, and never restores, since its backup is an older picture's.
- **A bulk run takes the library or the folders, never both** (`Bulk::run()['scope']`), and the window, the parked hold and `Queue`'s counts read both, since they share the service's queue. A new place that counts or sweeps what is on its way reads `Folders\Table::count_anywhere()` or `anywhere()` beside `Records`.
- **An Action Scheduler hook never takes a filter's or another action's name**: WordPress keeps actions and filters in one registry, so `apply_filters()` on a name an Action Scheduler step listens to runs that step, and the plugin's own `iminify_optimize_file` filter once called `Folders\Optimizer::optimize()` from inside itself until PHP ran out of stack. The folder pipeline's steps are `iminify_optimize_folder_file`, `iminify_check_folder_file` and `iminify_resume_folder_files` for that reason.
- **A WebP or AVIF of a copy's name that the record doesn't name as the plugin's, with the bytes it wrote, is never written over** (`Writer::put()`, both pipelines): another tool made it (EWWW writes `photo.jpg.webp` too), and once written over it would read as the plugin's and go with a restore or an uninstall. The skipped copy counts in the result's `skipped`.
- **A file is replaced, never rewritten in place:** `Media\Files::replace()` writes a temporary file beside it, checks it, and renames it over the old one, because WP_Filesystem's `move()` deletes the target first. A name inside a zip is never used as a path: `Media\Zip` reads only the entries the service's answer named.
- **The attachment metadata is read fresh right before it is saved, and only `filesize` and the main file's width and height change in it**, so keys other plugins keep there survive. The save runs with `Media\Writer::$writing` set, and the plugin's own hooks ignore it. A restore makes the sizes again with core (`Media\Restorer`), under the same guard, and merges what core made over the old metadata for the same reason.
- **A wait holds no runs.** An attachment waiting for the next batch reads `paused` and one waiting for the connection `parked`, with nothing scheduled, and `Media\Queue` is the one routine that sends them on, from the timer, "Start now" or the first `GET /site` that works. Queueing them one run each would make a long queue fire and refuse itself. Only a spent day stops every group (`Media\Pause`, on the `daily_limit_reached` code, never on a 429 alone: `rate_limited` is the same status and stays one attachment's wait), and a group already open always goes on, since its image is counted. A parked attachment keeps its group for the same reason.
- **`_iminify` is serialized, so nothing can query it.** `Media\Records::update()` also writes `_iminify_status` (which reads `restored` for a record that reads `not_optimized` with the code `restored`, so the bulk run can leave out an image someone put back), `_iminify_formats`, `_iminify_sizes`, and `_iminify_before` and `_iminify_after` (the bytes behind the bulk page's savings), which the queue, the bulk run and the media library's filters read. Change a record only through `Records`, or they drift.
- **The bulk run never queues the library at once** (`Media\Bulk`): a feeder hands `Optimizer` a window of images at a time as the `bulk` trigger, which always takes the slower lane and runs whatever the site's upload switch says. The window is counted in the files the service makes (each size in each format, an upper bound read from the registered sizes) and halves, with a hold on the feeder, whenever the service turns a bulk group away with `rate_limited`, so new uploads keep room; the service's own ceiling is never written here. Every place that queues an image again keeps its trigger (`Optimizer::trigger()`), or a bulk image paused by a spent day would come back as an upload and be refused by the upload switch. Which images a run takes comes from `Bulk::candidates()` alone.
- **"While this page is open" runs the plugin's due actions from the bulk page's requests** (`Bulk::step()`), each claimed from Action Scheduler first, so its own runner never runs one twice. They are claimed by hook (`Bulk::PAGE_HOOKS`), never by group: Action Scheduler refuses a claim by a group whose id it hasn't cached. The store keeps the claim's hooks as its filter for the rest of the request, so they are reset afterwards where the store allows it (the hybrid store of a site still moving Action Scheduler's older data doesn't, and runs no runner of its own in that request).
- **Never write over the only copy of an image with backups on.** No room for the backup, or a backup that can't be saved, leaves the image as it is with nothing counted (`disk_full`, `backup_failed`); it never goes on without one. Below `Media\Disk::RESERVE` no group opens, and each write is checked first, so a copy with no room is skipped and never recorded.
- **Optimizing an image again restores it first** (`Media\Optimizer::ask()`), because the service only replaces a file with a smaller one, so the plugin's last output would stand against a gentler level. A request that can't be taken now changes nothing.
- **Sending an image for what it lacks isn't optimizing it again** (`Media\Missing`, `Optimizer::fill()` and `send_for_missing()`, the record's `fill`): nothing goes back first, so its copies keep being served and nothing has to be made again. It goes from its original at the level it already has, so the service's rule that only a smaller file replaces leaves its files alone, and `Missing::merged()` adds to its result, keeping each file's `before`, or its savings would read as nothing. It reads `queued` or `waiting` on the way, like any image, but it never stopped being optimized: however that ends it reads optimized again (`Records::fail()` turns any failure into that, with the reason beside the image; `Records::end_fill()` for a stop and for nothing left to make), and a restore takes back whatever waits (`Bulk::take_back_fills()`), or Restore all would leave the plugin's files in place. An edit or a restore clears `fill` (`Records::bump()`), since the files it was for are gone.
- **What an image lacks has to leave the query once it's dealt with, or a run spends on it again every time.** A site's group takes the site's formats, so a run for one format makes them all, and it counts an image. `result.formats` is read from the group's answer, where the service names a WebP source's own format `original` (`Optimizer::asked_formats()` reads it as `webp`), and a group for sizes keeps the image's formats, since its copies cover the new sizes alone. `result.sizes` (`_iminify_sizes`) holds the sizes a record accounts for, those the image is too small for included; a look that finds nothing to make, or nothing a group can take, settles the image with no call (`Missing::settle()`). Finding the images is one query each (`Records::lacking()`), since the bulk page counts them on every poll. A size WordPress made from the plugin's own output (the file `wp_get_original_image_path()` names is one the plugin wrote) names no bytes in its group, so the service's file always takes its place; the record's `made` remembers those sizes across tries, since a try can end before its group opens.
- **WP-CLI drives the bulk run** (`Cli`): a command starts a run in the page's mode and calls `Bulk::step()` in a loop, so a run in the shell is a run on the page. A long process keeps every option and record it read, and a stale run written back would undo the page's Stop, so each look forgets them first (`Cli::forget()`). A wait no shell should sit through (a spent day, a lost connection) moves the run to the background and ends the command. A command checks no capability when no user is named, since whoever has the shell can reach the database, as with `wp action-scheduler run`; with `--user` it asks what the bulk page asks. The stall message shows `Admin\Bulk_State::COMMANDS`, so its command has to carry on a run that's going, whatever it does.
- **Admin screens draw state the server builds.** The settings page's script (`src/settings`) only draws what `Admin\State` answers through the plugin's REST routes (`iminify/v1`), and every call to the service happens behind them: the logic stays testable in PHP, and no answer ever carries the site key or a pairing's secret. The media library's script (`src/media`) only puts back the markup `Admin\Media_View` builds, through `Admin\Media_Controller`'s routes. The bulk page's script (`src/bulk`, Media > Bulk Optimization) draws what `Admin\Bulk_State` answers through `Admin\Bulk_Controller`; only its first load and a start or stop ask Iminify for the estimate, never its poll.
- **On a network the plugin is active for, the main site's connection is the network's** (`Network`, read from `active_sitewide_plugins`; active site by site, every site connects on its own). Its key lives in a network option, or is `IMINIFY_API_KEY`, which on a network is the network's and is never read by another site, since that site would send it from its own address; its pairing asks for a network, and only `manage_network_options` changes it (`Capabilities::NETWORK`), on Network Admin > Settings > Iminify, which draws the settings script for the main site's routes. Every other site keeps a key of its own, asked of the network's key from the network's address (`Network::join()`) in `Plugin::client()` alone, so only the background and the plugin's own pages ever join; every other place asks `Plugin::connected()`, which reads locally. One join at a time, the key read again past every cache once the lock is taken, because Iminify stops a site's earlier key when it gives a new one, and a refused key disconnects nothing while another request has since replaced it (`Connection::revoked_by_service()` compares the refusal's `key` fingerprint). A site disconnected on its own page or refused by Iminify is held (`Network::hold()`) while the network's key is the one it was held under, or a Disconnect on iminify.com would undo itself; a join's refusal holds it too, and a wait is waited out, since every site of a network shares the network's hourly allowance of joins.
- **Turning the plugin off for a network, and deleting it, walk every site it ran on** (`Lifecycle::each_site()`: the sites keeping `iminify_settings` or `iminify_activated`, which a site's first run adds in `Lifecycle::resume()`, so activating it for a network never walks the sites), each through `switch_to_blog()` with its own options, records and Action Scheduler tables. A cache kept for a request is keyed by site (`Picture`, `Shared`), since a page can switch sites. The network's key is stopped once, before the sites, which stops every key a site joined with, so those are never stopped on their own.
- **Who may do what lives in `Capabilities`**, which `iminify_capability` can change: `manage_options` for the settings and for bulk, since a run spends the account's day for the whole library, `manage_options` for the other folders too (`manage_network_options` on a network, where they are every site's), and `upload_files` with `edit_post` on that attachment for optimizing or restoring it, so what a screen offers and what its route takes can't drift apart. A new hook or a new argument on one goes in the readme's "For developers" list and in the service's WordPress guide.
- **`<picture>` serves only what the records prove** (`Media\Picture`): a copy whose origin is the plugin's, whose file still has the bytes written, beside a file that still has the bytes it had then (`for_bytes`, written by `Media\Writer`), so a picture replaced since never shows its old copy. Each source keeps every candidate of the `<img>`'s `srcset`, a width with no copy keeping its best file, so a missing copy never makes the browser fetch a larger width. Core filters the same markup more than once (a block theme's template runs the content filter again), so a wrapped `<img>` carries `data-iminify-picture` and is never wrapped twice, nor is one inside a `<picture>` someone wrote. An address under the uploads folder is matched to its file; one WP Offload Media serves from its bucket is matched only in the folder `wp_get_attachment_url()` gives that attachment, by one of its files' names, never with a query (a signed address is for one file), and any copy of an attachment WP Offload Media serves, whatever its address (WP Offload Media rewrites a local one it meets later in the page), is served only once the copy's record says it went up with the bytes it has (`offloaded`, `Compat\Offload_Media::in_bucket()`), since a `<source>` that fails shows a broken image. With WP Offload Media's "Remove Local Media" on, neither the copy nor its file is on the disk: the record's `offloaded` proves the copy, and the metadata's `filesize` the file beside it (`for_bytes`), so `Writer::save_metadata()` writes `filesize` for every declared output. Any other address (a CDN, another offload plugin) keeps its own, since the copy may not be there. WooCommerce's variation swap rewrites the product image's `src` and `srcset`, which a `<picture>` would hide behind its sources, so `Compat\Woocommerce` adds a few lines before WooCommerce's own variation script (never after: WordPress then takes `defer` off it and its dependencies): one observer on the whole document (a variation's own gallery replaces the gallery's markup) sets a product image's sources aside while its `src` or `srcset` differs from what WooCommerce stored in `data-o_src` and `data-o_srcset` before its first swap, so a change nothing stored (a lazy loader's) leaves them; `tests/e2e/specs/woocommerce.spec.js` runs the script from the PHP file. A source never takes the image's `wp-post-image` class instead, since WooCommerce then stores and puts back every attribute from the first source for all of them, and Reset empties the image's `src` and its zoom image. The wrapper is `<picture style="display: contents;">`, as core's Modern Image Formats writes it, so the `<img>` stays the box a layout sizes. With picture tags across the whole page (`Local_Settings::DELIVERY_PAGE`), core's filters keep wrapping what they reach and `Delivery\Buffer` reads the page through core's template buffer (`wp_template_enhancement_output_buffer`, which hands over a whole HTML answer and nothing else): every `<img>` they didn't wrap, outside any `<picture>`, goes through `Picture::wrap()` by its `wp-image-N` class, else by the attachment its address names (a page's images in one `Shared::named()` query, the first naming the file with copies to serve), and a file in a chosen folder through `Picture::wrap_with()` with its row's copies, proven the same way and read through `Folders::guard()`. It walks the page with `Delivery\Markup`, which reads each tag's place from the tag processor's bookmark, and builds the page again from the original bytes around the tags it wraps, never with a pattern; an address WP Offload Media serves is matched only through the class. A `style` attribute or a `<style>` element naming a background goes to `Delivery\Css`, whose one pass knows comments, strings, `url()` and parentheses (a `data:` address can hold semicolons and run to megabytes, so never a pattern there either): after each `background` or `background-image` declaration whose own `url()`s have proven copies (`Picture::image_set()`, `image_set_with()`, its addresses in the images' one lookup) it adds a copy of the declaration in which each such address becomes an `image-set()` of the copies by `type()`, the original last, so a browser that can't read it keeps the first; a copy rather than a longhand, since it then sets every other part as the first does and an invalid declaration stays invalid. A declaration holding a function the browser fills in only when it computes the value (`Css::LEFT`: `var()`, `env()`, `attr()`, `if()`, and a custom `--function()`) is left as it is at any depth, because it reads as valid everywhere, so a browser without `image-set()` would take the copy and show no background; keep that list whole. The buffer's filter runs at `Buffer::PRIORITY` (20), after core's own (10), which moves a classic theme's late-printed styles into the head. A `<style>` element is changed through core's `set_modifiable_text()`, which writes its line breaks as `\n`. A stylesheet in a file of its own never passes through the buffer. Nothing is wrapped on a wp-admin screen, in a feed or on an AMP page; admin-ajax answers are, since a theme's front-end requests come through it. `mark_pictures()` walks the markup with `WP_HTML_Tag_Processor`, never a pattern, which runs out of backtracking on a long unclosed tag and blanks the post.
- **The server's rules (`Delivery\Rules`, `Local_Settings::DELIVERY_RULES`) live in the site's own `.htaccess`** (WordPress's, in the home address's folder, told from `ABSPATH` by `Rules::file()`, never core's `get_home_path()`, which reads the running script and is wrong outside wp-admin), one block per site (`Rules::marker()`, matched as a whole line), never in the uploads folder, where a `RewriteEngine On` turns off every root rule below it (hotlink protection, a redirect). `Rules::place()` puts it at the end on a single site, so every rule already in the file runs before a copy is sent (a copy's second pass no longer matches a rule written for `.jpg`), and on a network right before `# BEGIN WordPress`, else at the top, since WordPress's network rules end the rewriting of a file that exists. A block is written only where the file already turns rewriting on, read and written under the same `flock` as core's `insert_with_markers()`, over the old text and cut where it ends, so a failed write never empties the file; a BEGIN line with no END line leaves the file alone. Anywhere else the settings show the lines to paste, and on Nginx lines for the server block, whose `Accept` checks stay at the server's level: an `if` inside a location skips its `try_files`. Its patterns are paths from that file's folder: the site's uploads folder (the main site's leaving `sites/N/` out) and, on the site that lists them, the chosen folders. `Vary: Accept` comes from mod_rewrite itself (a no-op rule with an `Accept` condition), since `mod_headers` is often off. `Rules::check()` asks the site for a test image of its own (written and deleted in that request), with and without AVIF accepted, each at an address of its own, following no redirect and sending the site's password only to its own host, and reads `cf-ray`; a 5xx to the plain request while the block is in takes it out and holds it out (`Rules::refused()`) until the person saves again (`sync( true )`), or every page load would break the site anew. The rules can only see that a copy exists, so while they're on, the plugin's own copy goes as soon as the plugin sees its file change (`Hooks::changed()` through `Copies::delete_stale()`, `Folders\Scanner::record()`), and `Rules::sweep()` takes the stale ones when the mode is turned on and when the plugin comes back on in it (`Lifecycle::resume()`), since it saw no change while off; another tool's copy beside an image is served too. A change of the delivery setting purges the page caches (`Caches::later( 'delivery' )`), through `add_option_` and `update_option_` of the setting. Rules come out in `Lifecycle::deactivate()` and on uninstall, and go back in `Lifecycle::resume()`.
- **Other plugins are reached only through their documented hooks and functions** (`includes/compat`), never their classes, which change between their releases. `Compat\Offload_Media` adds the plugin's own copies on the disk to the files WP Offload Media uploads (`as3cf_attachment_file_paths`, under `iminify-<file name>`) types each on its way up (`as3cf_object_meta`) and records it as in the bucket only once WP Offload Media says every file of that upload went up (`as3cf_post_handle_item_upload` with `true`), since its meta filter runs before anything is sent; the writer records the copies before it saves the metadata, which is what makes WP Offload Media upload them with their images, so keep that order, and a restore deletes the copies before WordPress makes the sizes again, since WP Offload Media uploads every file of its item still on the disk at each metadata save (`Media\Restorer`). `Compat\Caches` empties LiteSpeed Cache, WP Rocket, W3 Total Cache and Cloudflare's plugin when a bulk run ends, when a restore run that had restored images is stopped or paused (`Caches::OWED`), and at the end of any other request that restored an image or a file in another folder, or deleted their copies (`iminify_copies_deleted`, also fired by a restore that failed after deleting them; an update that replaced a theme or plugin holding a chosen folder, `Scanner::after_update()`), a run optimizing meanwhile included; never on an upload, which would empty every cache on every upload. Cloudflare's plugin reads its list of purging actions before this plugin loads, so its hooks object is called: `$GLOBALS['cloudflareHooks']`, or, under WP-CLI, which loads plugins inside a method, the object behind the `init` callback it always registers.
- **A file only in WP Offload Media's bucket is read from the metadata, never from the bucket** (`Compat\Offload_Media::only_in_bucket()` and `bytes()`: not on the disk, the attachment served from the bucket, and the metadata naming the file), so a screen, a count or a page costs no request to the bucket. Every read of an attachment's file that can meet one goes through them (`Records::wrote()` and `unchanged()`, `Originals::find()`, `Optimizer::why_not()`, `Declaration`, `Missing`, `Restorer`, `Picture`). A send or a restore brings back only the files it reads (`Offload_Media::bring_back()`, through WP Offload Media's copy-back filter, asked for that one file): its source, found through `Originals::fetch()`, which asks `find()` again of the file's own bytes, so only the disk ever decides that a file the plugin wrote is an original, and for a run for missing sizes the file WordPress makes them from. What came back is kept in the record's `fetched` and goes again (`put_away()`, in a `finally` around `Optimizer::optimize()`, `check()` and `Restorer::restore()`) while it has the bytes it came with and the plugin hasn't written over it, except an unsent group's source. Each output of an attachment WP Offload Media serves is declared `bucket` with the size the metadata gives it (`listed`), since any save of its metadata takes the files off the disk; `Writer` compares the metadata's size then for one gone by then. While a restore has WordPress make the sizes again, WP Offload Media's upload is held (`Offload_Media::hold()`, on `as3cf_pre_update_attachment_metadata`), so the files go up once, at the restore's own save. Core builds the original's path on the filtered attached file, which WP Offload Media answers with a path its stream wrapper reads from the bucket, and passes `wp_get_original_image_path()` through its filter even when asked for the unfiltered path: the plugin's own reads take `Originals::kept()`, and each core call that reads the original (`wp_get_missing_image_subsizes()`, `wp_update_image_subsizes()`) runs through `Offload_Media::locally()`. `Tests\Support\Offload_Stub` stands in for WP Offload Media in this mode, and its stream wrapper fails any test that reads a file through its bucket path.
- **Turning the plugin off leaves nothing scheduled, and no rules in the `.htaccess`** (`Lifecycle::deactivate()`; a bulk run reads paused and goes on once the plugin is on again): on a site where another plugin also loads Action Scheduler, a run whose plugin is off fails at once, so what was on its way is parked, keeping any open group, and goes on once the plugin is on again (`Lifecycle::resume()`, which also parks anything left queued with no run, since renaming the plugin's folder switches it off without its deactivation).
- **Deleting the plugin keeps every attachment's record while it keeps the copies or the backups** (`Lifecycle::uninstall()`, run by `uninstall.php`, which WordPress loads without the main file): the record is the only proof a file is the plugin's output, so without it a later install would send an optimized image for a second lossy pass. The copies and the backups go only when the person ticked it in the settings, and the key is stopped on Iminify unless it is set in `wp-config.php`. Never run uninstall in a development site by deleting the plugin from the Plugins screen or with `wp plugin uninstall` without `--skip-delete`: wp-env maps the plugin folder onto this checkout, so a deletion removes its files.
- **The suggested privacy text** (`Admin\Privacy`) and the readme's "External services" section say the same things about what is sent; change both together.
- **Every screen is built on the design system in `src/ui`**, never styled one at a time: its tokens (`_tokens.scss`: a cool grey scale and a sky accent, corners, shadows, motion), its parts (`_parts.scss` and `index.js`: buttons, status chips, panels, the progress bar and ring, callouts, the inline confirm, the shell command with its Copy button, toasts, the loading, empty and error states) and the pages' layout (`_page.scss`, through `screens.scss`). A new screen or state takes these parts; a part it lacks is added there. Every class, keyframe and property carries the prefix (`iminify-`, `--iminify-`), since the media panel's styles also load in the post editor, and the tokens are declared only on a root class (`.iminify-ui`, `.iminify-media`, `.iminify-notice`, `.iminify-toasts`), so a part drawn outside one has no colours. The page header (`Admin\Page_Header`) is printed in PHP with core's `.wp-header-end` after it, so other plugins' notices land below it.
- **The screens set no font.** They inherit WordPress's system font stack, which carries every script the plugin's languages need; a bundled Latin face would leave Arabic, Hebrew, Persian, Hindi, Thai, Chinese, Japanese and Korean on a fallback beside it. Letter spacing is turned off for those languages (`tokens.root`), since it pulls apart joined letters.
- **The accent is sky on every admin colour scheme; keyboard focus follows the person's scheme** (`--iminify-focus`): core's `--wp-admin-theme-color` from WordPress 7.0, and before it `--iminify-scheme`, which `Admin\Scheme::attach()` prints on each of the plugin's stylesheets, since WordPress 6.9 declares the scheme's colour only inside the block editor. A stylesheet the plugin adds calls `Scheme::attach()` too. Core's form controls inside the screens take the accent through `--wp-components-color-accent`, and their focus is restyled in `_page.scss` to the scheme's colour.
- **Direction is written with logical properties alone.** The build's right-to-left copy (rtlcss) flips physical ones, so a `[dir="rtl"]` rule would be flipped twice: anything that must not mirror is set in markup (the shell command's `dir="ltr"`, the ring's rotation as an SVG attribute), and an arrow is mirrored by `Icon`'s `flip`.
- **Motion honours `prefers-reduced-motion`**: every animation and transition stops under it (`_parts.scss`), and `Count` shows the new number at once. A spinner keeps turning, slowly, since it says the page is working.
- **Asking before something that can't be undone happens in the page, never in `window.confirm()`**: `Confirm` with `useAsk()` in the plugin's pages, which gives focus back to the button that opened it, and `ask()` in `src/media`, in the panel or, for a row action, under the row's actions (the Iminify column is hidden on a phone and can be hidden in Screen Options). Each opens with focus on Cancel, and Escape closes it without closing the media modal around it. What went well shows as a toast (`useToasts()`); a refusal stays on the page.
- **A number the browser formats uses Western digits** (`formatNumber()`, `numberingSystem: 'latn'`), as `number_format_i18n()` does on the server, so a counted number matches the ones beside it in every language.
- **Inside the attachment panel, use buttons, not selects or inputs.** The media modal's attachment fields save on every `change` event inside them and draw themselves again, which would throw a choice away.
- **Admin scripts are built with `@wordpress/scripts`** from `src/` into the gitignored `assets/build/` (`npm run build`). `src/` and `package.json` ship with the plugin so anyone can rebuild what it runs (directory guideline 4). WordPress's own packages (`@wordpress/components`, `element`, `i18n`, `api-fetch`) load as core's copies and are never installed here (of `@wordpress/components`, only the settings page's form controls are used; everything else is the design system's own), which `eslint.config.cjs` tells the linter, so use only what the oldest supported WordPress has. The build minifies only when `NODE_ENV` is unset or `production`.

## Tests and checks

- `composer lint`: PHPCS with WPCS and PHPCompatibilityWP.
- `composer types`: PHPStan at level 8 with the WordPress extension. The integration tests stay outside it, since nothing describes WordPress's test library to it.
- `composer test`: the unit tests in `tests/Unit`, PHPUnit 9 with Brain Monkey and no WordPress loaded.
- `npm run lint:js`: wp-scripts' ESLint and Prettier on `src/`; `npx wp-scripts lint-js src --fix` fixes the formatting.
- `npm run test:integration`: the integration tests in `tests/Integration`, on WordPress's own test library inside the test environment (start it first with `npm run env:test start`). WordPress's test library runs on PHPUnit 9 with Yoast's polyfills, so the suite does too. It turns the plugin's `CREATE TABLE` into a temporary table, whose rows the test site's database keeps through a test's rollback, so a test of the folders drops the table first (`FoldersTest::set_up()`), and one that makes files under `wp-content` removes them itself, since a run cut short leaves them behind. A test that makes a site on a network makes that site's Action Scheduler tables itself, never the main site's: those are real tables, and the schema's `ALTER TABLE` commits the test's transaction, leaking its rows into every later test and into the test database. A test that defines a constant runs in a separate process, which reuses the installed database (`tests/bootstrap-integration.php` sets `WP_TESTS_SKIP_INSTALL`), since a second install under the running suite breaks the network tests after it.
- Tests never reach the real service or use a real key: `tests/Support/Api_Stub.php` answers the API's calls through `pre_http_request`, from the answers in `tests/fixtures`, and a call nothing set up answers 404. WP-CLI isn't loaded there, so `tests/Support/Wp_Cli_Stub.php` stands in for it (`tests/phpstan/wp-cli.php` does for PHPStan), and a command's real output is checked with `wp iminify` in a wp-env site.
- `npm run test:e2e`: the browser tests in `tests/e2e/specs` (Playwright, Chromium), against the e2e site (`.wp-env.e2e.json` on port 8890; start it first with `npm run env:e2e start`). Its must-use plugin (`tests/e2e/mu-plugins`) answers every call to Iminify from `tests/fixtures` and keeps Action Scheduler and WP-Cron from running, so a test reads each image's state as a button left it; `tests/e2e/bin/seed.php` (through `tests/e2e/support/wp.js`) sets up each test's state. Connect's tab to www.iminify.com is answered by the test, never loaded. PHPStan leaves `tests/e2e` out, since its PHP is a WP-CLI script and a must-use plugin.
- Plugin Check: CI's action installs its latest release and fails on any warning (`strict`). A copy installed in a development site may be older and miss newer sniffs, so update it (`wp plugin update plugin-check`) before trusting a local pass. Its database sniff wants table names written as `{$wpdb->prefix}name` inside the query and every value bound through `prepare()`, ids included.
- `php bin/build.php` copies what ships into `build/iminify-image-optimizer`: the tracked files `.distignore` doesn't exclude, the built admin scripts (it stops when `npm run build` hasn't run), and Action Scheduler. Plugin Check runs on that copy.
- CI (`.github/workflows/ci.yml`) runs all of these, and Plugin Check on the build.

## The development WordPress

wp-env runs WordPress in Docker: `.wp-env.json` is the development site on port 8888, `.wp-env.test.json` the test site on 8889, `.wp-env.e2e.json` the browser tests' site on 8890 and `.wp-env.multisite.json` a subdirectory multisite network on 8891 (activate the plugin there with `wp plugin activate --network`). Stop each one you started when you are done (`npm run env stop`, `npm run env:test stop`, `npm run env:e2e stop`, `npm run env:multisite stop`). `npm run test:integration:multisite` runs the integration suite on a network (`WP_MULTISITE=1`), where `NetworkTest` runs instead of skipping; CI runs both.

Run `npm run build` once before opening the plugin's settings page there, or `npm run start` to rebuild as you edit.

To reach a development copy of the service, a gitignored `.wp-env.override.json` (and `.wp-env.multisite.override.json` for the network) maps `dev/mu-plugins` into `wp-content/mu-plugins` and sets the constants that plugin reads (`IMINIFY_API_BASE`, `IMINIFY_DEV_RESOLVE`, `IMINIFY_DEV_CA`; its header says what each is), with a certificate file kept in the gitignored `dev/local/`. `IMINIFY_API_KEY` there connects the development site with a key. Anything about one machine stays in those two ignored places, never in a tracked file.

The checkout is mounted into every wp-env site, so a script or test that edits the plugin's source files (a mutation check, a temporary debug line) can leave a site's web server serving the edited copy from OPcache after the file is put back, while WP-CLI in the same site runs the real one. After such an edit, reload the web server in each running site's WordPress container (`apache2ctl graceful`) before trusting anything a browser or a cron request does there.
