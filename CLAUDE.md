# Iminify Image Optimizer

The WordPress plugin for Iminify (https://www.iminify.com), an image optimization service. Its wordpress.org slug, main file and text domain are `iminify-image-optimizer`.

## The plugin is thin on purpose

The service decides everything it can: a site's settings, which outputs are worth keeping, every limit and count, the bulk estimate, the status and upgrade messages. The plugin does only what has to run inside WordPress: catch uploads, edits and deletions, send an attachment's image, write back what the service returns, keep and restore backups, print `<picture>` markup for copies that exist, keep its own per-attachment state, and show what the service says. A rule that could run on the service goes there, because code in a public plugin can be read and changed by anyone who installs it. Every number the plugin shows comes from the service's answers, never typed into its copy.

## Rules, each with its reason

- **PHP 7.4 syntax.** WordPress runs on PHP 7.4 and later, and about one site in seven is still on 7.4. So no union types, `match`, enums, `readonly`, constructor promotion, named arguments, the nullsafe operator, `mixed` or a `static` return type. PHPCompatibilityWP (in `composer lint`) holds the code to it. WordPress 5.9 and later polyfill `str_contains()`, `str_starts_with()` and `str_ends_with()`.
- **WordPress 6.9 and later**, the floor of the bundled Action Scheduler, which follows WordPress's latest release minus two.
- **WordPress's coding standards** (WPCS 3, `WordPress-Extra`): the directory's reviewers and its automated release scan read code against them. Run `composer lint`; `vendor/bin/phpcbf` fixes what it can.
- **Prefixes everywhere:** `iminify_` for functions, options, hooks, transients and post meta, `IMINIFY_` for constants, the namespace `Iminify\WordPress`, and the literal text domain `iminify-image-optimizer` in every translation call. A WordPress site shares one global scope with every other plugin.
- **A comment carries its whole reason.** It never cites a decision number, a work item or a document outside this repository, and never names another codebase's classes, settings or tables: a reader here has only this repository. Say what the other side does in plain words ("Iminify's import reads these keys").
- **Files:** classes live in `includes/` under WordPress's file names (`Key_Store` in `includes/class-key-store.php`, `Api\Client` in `includes/api/class-client.php`), which `includes/class-autoloader.php` maps. Every PHP file starts with the `ABSPATH` guard.
- **No runtime libraries but Action Scheduler.** Two plugins that bundle different versions of one library break each other on the same site. Action Scheduler is the exception by design: it is loaded from the main file before `plugins_loaded`, never prefixed, and the newest copy on a site runs.
- **Every call to the service goes through `Api\Client`** on WordPress's HTTP functions, with TLS verified and no redirect followed. The site key is stored sealed (`Key_Store`), and is never printed, never sent to a browser, never put in a REST answer or a script.
- **Nothing reaches the service before the site is connected** (directory guideline 7): no call on activation, no telemetry, no remote assets.
- **Nothing that runs locally is locked by plan** (directory guideline 5): restore, serving WebP and AVIF copies that exist, the bulk screens, WP-CLI and backups keep working on any plan, with the day's images spent, or disconnected. Only the service refuses work.
- **Notices only on the plugin's own screens**, plus at most one dismissible notice elsewhere; no admin bar item and nothing on the front end by default but the `<picture>` markup and the few lines `Compat\Woocommerce` adds to WooCommerce's variation script (guidelines 10 and 11). Reading whole pages (`Delivery\Buffer`), filling in the width, height and alt text an image's markup lacks (`Delivery\Complete`) and writing rules into the site's `.htaccess` (`Delivery\Rules`) are settings the person turns on.
- **Files the plugin writes go under the uploads folder, or over the images in the folders someone chose** (`Folders`), never into its own folder, which every update replaces. The exceptions are its marked block in the site's `.htaccess` (`Delivery\Rules`), and, on the person's press alone, taking out the rules another optimizer left in the files it wrote them to (`Switching\Leftovers`, below). Backups live under the uploads folder in `Media\Paths::BACKUP_FOLDERS`: the library's in `iminify-backup/`, the other folders' in `iminify-backup-folders/` at their path in `wp-content`, since a path in the uploads folder can be anything and no name inside `iminify-backup/` is safe from an attachment's.
- **Optimizing runs in the background and never waits.** An upload, an edit or regenerated sizes only queues the attachment (`Media\Hooks`), since an upload request is already busy making sizes. `Media\Optimizer`'s Action Scheduler actions open a group, send the original and check back later: a `Retry-After`, a group still being made or an outage becomes the next run's time, never a `sleep()`, and a spent day holds no run at all (below).
- **An attachment's record (`Media\Records`, the `_iminify` post meta), and a file's row in `Folders\Table` for an image in another folder, is the only proof a file is the plugin's own.** It names every file the plugin wrote over, with the bytes it wrote, and every WebP or AVIF copy with its origin: `iminify` for the plugin's own, or the short name of the plugin whose copy it took over (`Copies::taken()`, below). The original comes only from `Media\Originals::find()`, which never answers a file the plugin wrote, only its backup, so no image is compressed twice. Since a file is renamed into place before its record can name it, `Media\Writer::put()` hands its caller a journal first (the record's `pending`: each file and copy about to be written, with its bytes), and `Records::get()` and `Folders\Table` take a file that has those bytes as the plugin's own (`Writer::settle()`, a copy never served until it is written again), so a request that dies between the rename and the save of the record still leaves the proof. A new path that writes the plugin's files goes through `put()` with a journal, and the write's own save empties `pending`. Delete only copies whose recorded origin is the plugin's (`Copies::own()`); every path that deletes copies only forgets a taken one and leaves its file.
- **An image never passes through PHP's memory whole.** A source goes out as a file cURL reads from the disk (`Api\Upload`: the request carries no body and `Upload::ARGUMENT`, and the `http_api_curl` action hands cURL a `CURLFile`), and a zip entry is copied into its temporary file a piece at a time (`Zip::extract()`), so an original as large as the plan takes goes through on a 128 MB limit. Where WordPress can't send over cURL the body is built in memory, and `Upload::max_bytes()` caps the source `Originals::find()` may answer, so a larger original gives way to WordPress's `-scaled` copy. The test stub sees `Upload::ARGUMENT`, never the bytes.
- **Attachments that share their files have one holder** (`Media\Shared`): WPML and Polylang translate an image by adding attachments that name the same `_wp_attached_file`. Only the holder (the one whose record has work on the files, else the lowest id) is ever sent; the others read `shared` in `Optimizer::why_not()`, `Originals::find()` answers nothing for them, `Hooks` queues the holder for any change to their files, and deleting one deletes nothing the files still need, the holder's record moving to the next (`Shared::leaves_files()`). A new path that sends, restores or deletes an image's files goes through the holder too. Post meta has no index on its value, so who names a file is kept for the request (`Shared::others()`), dropped when an attachment's file changes, before each Action Scheduler action and on each WP-CLI look; a path that writes or deletes files asks afresh (`$fresh`, as `Optimizer::optimize()`, `Hooks` and `Shared::leaves_files()` do), so no kept answer can send a translation's files. Names match byte for byte, since the column's collation ignores case. A screen or run that asks about a page of images primes them in one query first (`Shared::prime()`, which `the_posts` does for the media screens' queries). A file another attachment's record keeps a backup of is never an original (`Originals::find()`), since it is that one's output, as when a translation plugin leaves a translation on its holder's old file after an edit. `wpml-config.xml` keeps every `Records::ALL_META` key out of WPML's and Polylang's copies, which `SharedTest` pins. Each of the others keeps the holder's id in its record (`holder`, written by `Shared::point()`) wherever the holder is already known: the look over the library for a holder with copies taken over from another plugin (`Others::walk()`), the holder's finish (`Optimizer::finish()`, asked afresh), a set-aside (`Optimizer::skip()`, the bulk run's too), `Hooks::changed()`, `Shared::leaves_files()`, and an attachment coming to name a file with a copy or a backup of the plugin's (`Shared::file_changed()`, which asks nothing of a new upload's name, since it has neither). `Picture::source()` follows it one step, only while both name the same file byte for byte, so a pointer left behind serves nothing; it is no work (`holds_work()` ignores it), and a page reads its translations' holders in one go (`Picture::prime()`, from `prime_content()` before core's `wp_filter_content_tags` and from the buffer).
- **A regeneration's sizes name no bytes** (`Optimizer::regenerated()`): when WordPress made sizes again from a main file the plugin wrote (Regenerate Thumbnails, `wp media regenerate`), they are copies of a copy, so their group declares them without bytes and the service's files, made from the backup, replace them.
- **The background queue's requests to the site itself carry its basic-auth password** (`Loopback`, on `cron_request` and Action Scheduler's async request): `IMINIFY_AUTH_USER` and `IMINIFY_AUTH_PASSWORD` from wp-config.php, else the credentials the request making them came with, outside REST and XML-RPC. Nothing is stored, and calls to the service never carry them.
- **Other folders go through their own pipeline beside the library's** (`Folders\Optimizer`, `Folders\Restorer`, `Folders\Scanner`), one group per file with no sizes and `keep_dimensions`, which Iminify reads only from a site key so a theme's image keeps its width and height whatever the site's maximum width and size limit. What a refusal means is one decision for both (`Media\Refusal::decide()`); a change to it goes there, never into one pipeline. `Media\Writer::put()` writes either's files under its root.
- **A file in another folder is read or written only through `Folders::guard()`**, which asks again of the file's real path what `Folders::check()` asked of the folder: inside a chosen folder in `wp-content`, outside the uploads folder, the plugin's own folder, the tool folders (`Folders::TOOL_FOLDERS`) and hidden or dependency folders, and no link on the way. A row is data anyone with the database could have written, so a path from it is never trusted on its own; a copy is deleted only beside its file, and the list shows a file's picture only from a path the guard passes (`Folders_State::thumb()`).
- **The folders' rows outlive the list.** Taking a folder off the list keeps its rows, and a file a scan no longer finds reads `missing`, since each row is the proof of what the plugin wrote; a scan finding it again puts it back where it stood. The table is made with the first folder (`Table::create()`), never on a site that chooses none, on `base_prefix`, and goes only when uninstall deletes both the copies and the backups. On a network only the main site lists folders (`Folders::available()`), since every site shares `wp-content`.
- **A scan walks under a time budget and goes on where it stopped** (`Scanner::step()`, its queue of folders kept in an option, at least one folder a step), since a folder can hold more files than a request can look at; a run over the folders refuses to start while one is under way. A file whose bytes are no longer what the plugin wrote or last saw has changed: it reads not optimized, and never restores, since its backup is an older picture's.
- **A bulk run takes the library or the folders, never both** (`Bulk::run()['scope']`), and the window, the parked hold and `Queue`'s counts read both, since they share the service's queue. A new place that counts or sweeps what is on its way reads `Folders\Table::count_anywhere()` or `anywhere()` beside `Records`.
- **An Action Scheduler hook never takes a filter's or another action's name**: WordPress keeps actions and filters in one registry, so `apply_filters()` on a name an Action Scheduler step listens to runs that step, and the plugin's own `iminify_optimize_file` filter once called `Folders\Optimizer::optimize()` from inside itself until PHP ran out of stack. The folder pipeline's steps are `iminify_optimize_folder_file`, `iminify_check_folder_file` and `iminify_resume_folder_files` for that reason.
- **A WebP or AVIF of a copy's name is written over only when the record names it with its bytes (the plugin's own, or one it took over), or another optimizer's records name it now** (`Writer::put()`, its `$theirs` from `Takeover::named()`; the folders pass none): the plugin's own copy of the same name replaces that optimizer's in place (EWWW, Imagify and LiteSpeed write `photo.jpg.webp` too), the one write over another plugin's file the switching rules allow. Anything else at that name another tool made, and once written over it would read as the plugin's and go with a restore or an uninstall, so it is answered in `kept`, never in `skipped`, which is for faults. A taken copy stops being served (its entry dropped, its file left) once the plugin writes over the file it stands beside, or makes its own copy of that file in that format under its own name (ShortPixel's `photo.webp` beside the plugin's `photo.jpg.webp`).
- **Another optimizer's work is read, never done again by itself** (`includes/switching`). One reader per optimizer (`Switching\Reader`, ten of them) answers from what that plugin left (its post meta, its tables, its backups, and for LiteSpeed and Image Optimizer by Elementor, which record no bytes per file, what they did to the files), active or not; a plugin that only makes copies elsewhere or takes images away (Converter for Media, whose copies a reader answers in `outside`, and Optimole, `Reader::away()`) is never asked for an optimization (`compresses()`). Where a plugin records no bytes for what it wrote (a run Smush never finished, ShortPixel's format conversion), its files are its output with no original while the trace that says so is there (`Reader::held()`: Smush's backup and its pointer, ShortPixel's record of the conversion, which their own restores remove), since reading them as originals would send them for a second lossy pass. Modern Image Formats keeps its records in each attachment's metadata, so a send asks its reader whatever the site's cached look says (`Reader::in_metadata()`). A file whose bytes are still those the plugin recorded writing is its output, unless it has the bytes Iminify wrote there (`Reader::answer()`, since a reader that records no bytes, Image Optimizer by Elementor's converted branch, claims any file at its name): never an original (`Originals::find()` answers only its backup, and only one with the bytes that plugin recorded before its first pass), never sent (`Optimizer::why_not()` answers `other_plugin`, read afresh at each send, which is the guard; `Folders\Optimizer::why_not()` for the files it optimized through its own folders). The record's `other` status and `Records::OTHER_META` serve the screens and the counts, and its `other.outputs` (each output's bytes) stand in for the other plugin's records once that plugin deleted them, while the files keep those bytes (`Others::remembered()`): `Others::look()` writes them when the other plugin's records change (the bulk page's first load and the media library ask), and takes them off an image no reader claims and whose files changed. Uninstall keeps such a record while it names the plugin's own backups or copies. Such an image is restored from the original that plugin kept (`Restorer`, asked before its "nothing to restore", which is only for the plugin's own work), copied into place, never moved; where restoring is that plugin's own to do (a conversion that changed the attachment's address; EWWW's cloud backups) the reader says why (`elsewhere`), and Restore all leaves such images out (only a person naming one restores it). Every path a record gives goes through `Switching\Places` (the uploads folder, the network's, `wp-content/ewww/image-backup`, `wp-content/uploads-webpc`, no link on the way), and nothing another plugin made is moved, renamed or deleted, but for the leftover rules someone removes on the settings page (below). A reader that doesn't know what it finds answers nothing.
- **Another optimizer's WebP and AVIF copies are taken over, never made the plugin's to delete** (`Switching\Takeover`): a copy its records name (`Reader::read()`'s `copies`, each with the file it stands beside, and Converter for Media's `outside`), that reads as its format and is no older than its file, is recorded with that plugin's short name as its origin, its `bytes` and the file's `for_bytes`, by the look over the library (`Others::walk()`), on images that are not the plugin's own work, which also points the image's translations to it (`Shared::point()`) so their pages serve them too. A copy a record places in another folder than its file is never taken, since `<picture>` addresses a copy beside its file, a copy taken before against other bytes of its file is never taken again, since the times alone can't tell a picture replaced in the same second, and a file an attachment holds as its own (someone's upload named `photo.jpg.webp`, which WordPress keeps) is never another plugin's copy, taken or written over (`Takeover::named()`). LiteSpeed's are never taken, since no record of its names them. Deleting a reader's plugin (Converter for Media's uninstall deletes its copies) looks at the library again and empties the page caches (`Others::deleted()`, the `others` purge). `Copies::delete_own()`, `delete_stale()` and `forget_gone()` forget a taken copy (`Copies::unproven()` for one that can't be served any more) and never touch its file; the media panel says whose copies its pages are served, and offers no button for them, since the next look would take them over again. The other folders take none over.
- **LiteSpeed Cache, active, answers WordPress making an image's metadata in the `create` context** (an upload, a regeneration, a replaced image) on admin requests, at priority 10, before the plugin's own hook: it deletes every `.webp` and `.avif` beside the image's files, the plugin's own included, and moves its `.bk.` backups back over them. So `Hooks::changed()` forgets the plugin's own copies that are gone (`Copies::forget_gone()`, which also takes their format off the result, so `Missing` finds the image lacking it) and reads a file put back as changed, never optimized; the bulk page says so while LiteSpeed is active (`Bulk_State`'s `putback`).
- **While another optimizer acts on uploads, nothing is sent** (`Others::acting()`: active, with its own optimization of uploads on): an upload's run reads `not_optimized` with `other_optimizer`, a press and a bulk start are refused, and a bulk run already going holds with that `reason` and looks again from its start once it stops, since the images it had sent read not optimized; the settings, bulk and folders pages and the one notice name it and what to switch off. Restoring and serving copies go on.
- **A file is replaced, never rewritten in place:** `Media\Files::replace()` writes a temporary file beside it, checks it, and renames it over the old one, because WP_Filesystem's `move()` deletes the target first. A name inside a zip is never used as a path: `Media\Zip` reads only the entries the service's answer named.
- **The attachment metadata is read fresh right before it is saved, and only `filesize` and the main file's width and height change in it**, so keys other plugins keep there survive. The save runs with `Media\Writer::$writing` set, and the plugin's own hooks ignore it. A restore makes the sizes again with core (`Media\Restorer`), under the same guard, and merges what core made over the old metadata for the same reason.
- **A wait holds no runs.** An attachment waiting for the next batch reads `paused` and one waiting for the connection `parked`, with nothing scheduled, and `Media\Queue` is the one routine that sends them on, from the timer, "Start now" or the first `GET /site` that works. Queueing them one run each would make a long queue fire and refuse itself. Only a spent day stops every group (`Media\Pause`, on the `daily_limit_reached` code, never on a 429 alone: `rate_limited` is the same status and stays one attachment's wait), and a group already open always goes on, since its image is counted. A parked attachment keeps its group for the same reason.
- **`_iminify` is serialized, so nothing can query it.** `Media\Records::update()` also writes `_iminify_status` (which reads `restored` for a record that reads `not_optimized` with the code `restored`, so the bulk run can leave out an image someone put back), `_iminify_formats`, `_iminify_sizes`, and `_iminify_before` and `_iminify_after` (the bytes behind the bulk page's savings), which the queue, the bulk run and the media library's filters read. Change a record only through `Records`, or they drift.
- **The bulk run never queues the library at once** (`Media\Bulk`): a feeder hands `Optimizer` a window of images at a time as the `bulk` trigger, which always takes the slower lane and runs whatever the site's upload switch says. The window is counted in the files the service makes (each size in each format, an upper bound read from the registered sizes) and halves, with a hold on the feeder, whenever the service turns a bulk group away with `rate_limited`, so new uploads keep room; the service's own ceiling is never written here. Every place that queues an image again keeps its trigger (`Optimizer::trigger()`), or a bulk image paused by a spent day would come back as an upload and be refused by the upload switch. During a spent day a background run's look schedules the next one for when the batch opens, so whatever lifts the pause sooner wakes it: `Pause::lift()` calls `Bulk::wake()`, which moves the next look to now; keep that call wherever the pause ends. Which images a run takes comes from `Bulk::candidates()` alone.
- **"While this page is open" runs the plugin's due actions from the bulk page's requests** (`Bulk::step()`), each claimed from Action Scheduler first, so its own runner never runs one twice. They are claimed by hook (`Bulk::PAGE_HOOKS`), never by group: until Action Scheduler's data migration has run, which takes the scheduled tasks a stalled site lacks, its hybrid store refuses a claim by group ("The group "iminify" does not exist"), as a fresh wp-env site shows. The store keeps the claim's hooks as its filter for the rest of the request, so they are reset afterwards where the store allows it (the hybrid store of a site still moving Action Scheduler's older data doesn't, and runs no runner of its own in that request).
- **Never write over the only copy of an image with backups on.** No room for the backup, or a backup that can't be saved, leaves the image as it is with nothing counted (`disk_full`, `backup_failed`); it never goes on without one. Below `Media\Disk::RESERVE` no group opens, and each write is checked first, so a copy with no room is skipped and never recorded.
- **Optimizing an image again restores it first** (`Media\Optimizer::ask()`), because the service only replaces a file with a smaller one, so the plugin's last output would stand against a gentler level. A request that can't be taken now changes nothing. An image another optimizer compressed is optimized again the same way, only when someone asks (`Optimizer::redoable()`: the media library's press, the bulk run's `redo`, `wp iminify optimize --others`): it is put back from that plugin's original first (`Restorer`), at the press after every refusal that costs nothing, and for the bulk in its own run right before its group opens (`Optimizer::put_back_theirs()`), never in the feeder, so a wait never leaves it restored and unsent and it is an ordinary image by the time it goes. `why_not()`'s `$redo` reads that plugin's output as no reason only for such an image, whose run re-reads the readers before restoring, so no automatic path sends another plugin's output. It keeps a backup whatever the setting (the record's `redo`), or restoring it would end with that plugin's backup, and a stop gives back an image not put back yet (`Others::mark()`). An image that plugin converted into WebP or AVIF (Image Optimizer by Elementor's `photo.webp`, Modern Image Formats' `photo.avif`) has nothing put back, since its JPEG would change the attachment's address: `Originals::converted()` answers the JPEG or PNG it kept (the reader's backup of the main file, in another format than the files) as `Originals::CONVERTED`, never `ORIGINAL`, so the plan's file size still applies; `Declaration` reads the attachment's format from its file, declares its sizes in it and names it in `output_format`, which the service makes each output in, and the group records it as `made` for `Writer` and `asked_formats()`; at someone's ask every output is named without bytes, since nothing went back first (`Optimizer::made_again()`), and otherwise only a file the plugin didn't write. The JPEG is kept in the plugin's backup under its own name whatever the setting, and the record's `converted` (its path, the plugin, the files' format) makes that backup the source of every later send (optimizing again, missing formats and sizes, a regeneration) while the main file holds the bytes Iminify wrote in that format, so an edit or that plugin's own Restore ends it. `Restorer::availability()` answers `THEIRS` for such an image before anything else, so the JPEG never goes over its files, Restore all passes it over (`Bulk::candidates()`), and `Others::elsewhere()` gives that plugin's sentence from the record once no reader claims the files (`Reader::restore_elsewhere()`).
- **Sending an image for what it lacks isn't optimizing it again** (`Media\Missing`, `Optimizer::fill()` and `send_for_missing()`, the record's `fill`): nothing goes back first, so its copies keep being served and nothing has to be made again. It goes from its original at the level it already has, so the service's rule that only a smaller file replaces leaves its files alone, and `Missing::merged()` adds to its result, keeping each file's `before`, or its savings would read as nothing. It reads `queued` or `waiting` on the way, like any image, but it never stopped being optimized: however that ends it reads optimized again (`Records::fail()` turns any failure into that, with the reason beside the image; `Records::end_fill()` for a stop and for nothing left to make), and a restore takes back whatever waits (`Bulk::take_back_fills()`), or Restore all would leave the plugin's files in place. An edit or a restore clears `fill` (`Records::bump()`), since the files it was for are gone.
- **What an image lacks has to leave the query once it's dealt with, or a run spends on it again every time.** A site's group takes the site's formats, so a run for one format makes them all, and it counts an image. `result.formats` is read from the group's answer, where the service names the outputs' own format `original` (`Optimizer::asked_formats()` reads it through the group's `made` type, so a WebP source's reads as `webp`, and an AVIF attachment's WebP counts as asked, since none is made beside an AVIF file), and a group for sizes keeps the image's formats, since its copies cover the new sizes alone. `result.sizes` (`_iminify_sizes`) holds the sizes a record accounts for, those the image is too small for included; a look that finds nothing to make, or nothing a group can take, settles the image with no call (`Missing::settle()`). Finding the images is one query each (`Records::lacking()`), since the bulk page counts them on every poll. A size WordPress made from the plugin's own output (the file `wp_get_original_image_path()` names is one the plugin wrote) names no bytes in its group, so the service's file always takes its place; the record's `made` remembers those sizes across tries, since a try can end before its group opens.
- **WP-CLI drives the bulk run** (`Cli`): a command starts a run in the page's mode and calls `Bulk::step()` in a loop, so a run in the shell is a run on the page. A long process keeps every option and record it read, and a stale run written back would undo the page's Stop, so each look forgets them first (`Cli::forget()`). A wait no shell should sit through (a spent day, a lost connection) moves the run to the background and ends the command. A command checks no capability when no user is named, since whoever has the shell can reach the database, as with `wp action-scheduler run`; with `--user` it asks what the bulk page asks. The stall message shows `Admin\Bulk_State::COMMANDS`, so its command has to carry on a run that's going, whatever it does: `wp iminify run` alone, never Action Scheduler's `run --group=iminify`, which the same hybrid store refuses.
- **Admin screens draw state the server builds.** The settings page's script (`src/settings`) only draws what `Admin\State` answers through the plugin's REST routes (`iminify/v1`), and every call to the service happens behind them: the logic stays testable in PHP, and no answer ever carries the site key or a pairing's secret. The media library's script (`src/media`) only puts back the markup `Admin\Media_View` builds, through `Admin\Media_Controller`'s routes. The bulk page's script (`src/bulk`, Media > Bulk Optimization) draws what `Admin\Bulk_State` answers through `Admin\Bulk_Controller`; only its first load and a start or stop ask Iminify for the estimate, never its poll. The page audit's script (`src/audit`, Media > Page Audit) draws what `Admin\Audit_State` answers through `Admin\Audit_Controller`: Iminify keeps every audit, so the plugin only matches each image address to its attachment and size (`Audit\Resolver`) and gives each finding, problem and fix its own words (`Audit\Findings`). An address no attachment has is shown as text, never loaded as an image, since it can be on any host. Which fix a row offers is `Audit\Fixes`' to decide, and each goes through what the plugin already does: Optimize and AI alt text through the media library's routes (`/media/{id}/optimize`, `/media/{id}/alt-text`), so they keep its capability check and its refusals; the width, height and alt text a page's markup lacks through `Delivery\Complete`, which `/audit/complete` turns on for someone who may also change the settings; a smaller size is named for the person to pick in the editor, or where their theme shows the image when the audited post's content doesn't hold it (`Fixes::in_content()`), since the plugin never rewrites a post; a fill is offered only for an image whose address the page's buffer can match (`fill`, under the uploads folder). An audit is what Iminify saw then, so a fix never hides a finding: the screen asks for another scan.
- **On a network the plugin is active for, the main site's connection is the network's** (`Network`, read from `active_sitewide_plugins`; active site by site, every site connects on its own). Its key lives in a network option, or is `IMINIFY_API_KEY`, which on a network is the network's and is never read by another site, since that site would send it from its own address; its pairing asks for a network, and only `manage_network_options` changes it (`Capabilities::NETWORK`), on Network Admin > Settings > Iminify, which draws the settings script for the main site's routes. Every other site keeps a key of its own, asked of the network's key from the network's address (`Network::join()`) in `Plugin::client()` alone, so only the background and the plugin's own pages ever join; every other place asks `Plugin::connected()`, which reads locally. One join at a time, the key read again past every cache once the lock is taken, because Iminify stops a site's earlier key when it gives a new one, and a refused key disconnects nothing while another request has since replaced it (`Connection::revoked_by_service()` compares the refusal's `key` fingerprint). A site disconnected on its own page or refused by Iminify is held (`Network::hold()`) while the network's key is the one it was held under, or a Disconnect on iminify.com would undo itself; a join's refusal holds it too, and a wait is waited out, since every site of a network shares the network's hourly allowance of joins.

A source never takes the image's `wp-post-image` class instead, since WooCommerce then stores and puts back every attribute from the first source for all of them, and Reset empties the image's `src` and its zoom image. The wrapper is `<picture style="display: contents;">`, as core's Modern Image Formats writes it, so the `<img>` stays the box a layout sizes. With picture tags across the whole page (`Local_Settings::DELIVERY_PAGE`), core's filters keep wrapping what they reach and `Delivery\Buffer` reads the page through core's template buffer (`wp_template_enhancement_output_buffer`, which hands over a whole HTML answer and nothing else): every `<img>` they didn't wrap, outside any `<picture>`, goes through `Picture::wrap()` by its `wp-image-N` class, else by the attachment its address names (a page's images in one `Shared::named()` query, the first naming the file with copies to serve), and a file in a chosen folder through `Picture::wrap_with()` with its row's copies, proven the same way and read through `Folders::guard()`. It walks the page with `Delivery\Markup`, which reads each tag's place from the tag processor's bookmark, and builds the page again from the original bytes around the tags it wraps, never with a pattern; an address WP Offload Media serves is matched only through the class. A `style` attribute or a `<style>` element naming a background goes to `Delivery\Css`, whose one pass knows comments, strings, `url()` and parentheses (a `data:` address can hold semicolons and run to megabytes, so never a pattern there either): after each `background` or `background-image` declaration whose own `url()`s have proven copies (`Picture::image_set()`, `image_set_with()`, its addresses in the images' one lookup) it adds a copy of the declaration in which each such address becomes an `image-set()` of the copies by `type()`, the original last, so a browser that can't read it keeps the first; a copy rather than a longhand, since it then sets every other part as the first does and an invalid declaration stays invalid. A declaration holding a function the browser fills in only when it computes the value (`Css::LEFT`: `var()`, `env()`, `attr()`, `if()`, and a custom `--function()`) is left as it is at any depth, because it reads as valid everywhere, so a browser without `image-set()` would take the copy and show no background; keep that list whole. The buffer's filter runs at `Buffer::PRIORITY` (20), after core's own (10), which moves a classic theme's late-printed styles into the head. A `<style>` element is changed through core's `set_modifiable_text()`, which writes its line breaks as `\n`. A stylesheet in a file of its own never passes through the buffer. Nothing is wrapped on a wp-admin screen, in a feed or on an AMP page; admin-ajax answers are, since a theme's front-end requests come through it. `mark_pictures()` walks the markup with `WP_HTML_Tag_Processor`, never a pattern, which runs out of backtracking on a long unclosed tag and blanks the post.
- **The server's rules (`Delivery\Rules`, `Local_Settings::DELIVERY_RULES`) live in the site's own `.htaccess`** (WordPress's, in the home address's folder, told from `ABSPATH` by `Rules::file()`, never core's `get_home_path()`, which reads the running script and is wrong outside wp-admin), one block per site (`Rules::marker()`, matched as a whole line), never in the uploads folder, where a `RewriteEngine On` turns off every root rule below it (hotlink protection, a redirect). `Rules::place()` puts it at the end on a single site, so every rule already in the file runs before a copy is sent (a copy's second pass no longer matches a rule written for `.jpg`), and on a network right before `# BEGIN WordPress`, else at the top, since WordPress's network rules end the rewriting of a file that exists. - `composer test`: the unit tests in `tests/Unit`, PHPUnit 9 with Brain Monkey and no WordPress loaded.
- `npm run lint:js`: wp-scripts' ESLint and Prettier on `src/`; `npx wp-scripts lint-js src --fix` fixes the formatting.
- `npm run test:integration`: the integration tests in `tests/Integration`, on WordPress's own test library inside the test environment (start it first with `npm run env:test start`). WordPress's test library runs on PHPUnit 9 with Yoast's polyfills, so the suite does too. It turns the plugin's `CREATE TABLE` into a temporary table, whose rows the test site's database keeps through a test's rollback, so a test of the folders drops the table first (`FoldersTest::set_up()`), and one that makes files under `wp-content` removes them itself, since a run cut short leaves them behind. A test that makes a site on a network makes that site's Action Scheduler tables itself, never the main site's: those are real tables, and the schema's `ALTER TABLE` commits the test's transaction, leaking its rows into every later test and into the test database. A test that defines a constant runs in a separate process, which reuses the installed database (`tests/bootstrap-integration.php` sets `WP_TESTS_SKIP_INSTALL`), since a second install under the running suite breaks the network tests after it. A run puts the uploads folder back as it found it when it ends (`Tests\Support\Uploads_Sweep`, started from the bootstrap in the run's own process alone): every image a test uploads stays there otherwise, and WordPress's test library lists that whole folder at the start of each PHP process, so a folder left to grow over many runs made every process start tens of seconds slower through a container's file sharing. It deletes only what the run added, never a file that was there before, since a development site can share the folder; a run cut short leaves its files, so empty the test site's `wp-content/uploads` after one.
- Tests never reach the real service or use a real key: `tests/Support/Api_Stub.php` answers the API's calls through `pre_http_request`, from the answers in `tests/fixtures`, and a call nothing set up answers 404. WP-CLI isn't loaded there, so `tests/Support/Wp_Cli_Stub.php` stands in for it (`tests/phpstan/wp-cli.php` does for PHPStan), and a command's real output is checked with `wp iminify` in a wp-env site.
- `npm run test:e2e`: the browser tests in `tests/e2e/specs` (Playwright, Chromium), against the e2e site (`.wp-env.e2e.json` on port 8890; start it first with `npm run env:e2e start`). Its must-use plugin (`tests/e2e/mu-plugins`) answers every call to Iminify from `tests/fixtures` and keeps Action Scheduler and WP-Cron from running, so a test reads each image's state as a button left it; `tests/e2e/bin/seed.php` (through `tests/e2e/support/wp.js`) sets up each test's state. `wp.js` runs WP-CLI through `docker compose exec` on the compose file wp-env wrote for the e2e site (`wp-env status --json` names it), as `wp-env run` does, since `wp-env run` starts Node and reads its configuration again on every call, seconds each; a test that runs anything else in the site goes through `wp()` too. `IMINIFY_E2E_CLI`, when set, is that command instead, its words separated by spaces (`docker exec -i -w /var/www/html <container>`), for a site this process's wp-env can't describe, as when wp-env runs inside WSL and the browser on Windows. Connect's tab to www.iminify.com is answered by the test, never loaded. PHPStan leaves `tests/e2e` out, since its PHP is a WP-CLI script and a must-use plugin.
- Plugin Check: CI's action installs its latest release and fails on any warning (`strict`). A copy installed in a development site may be older and miss newer sniffs, so update it (`wp plugin update plugin-check`) before trusting a local pass. Its database sniff wants table names written as `{$wpdb->prefix}name` inside the query and every value bound through `prepare()`, ids included.
- `wp eval-file bin/i18n.php check` (in a wp-env site, after a production `npm run build`): the translations' template holds every string the code does. `TranslationsTest` checks each locale against it.
- `php bin/build.php` copies what ships into `build/iminify-image-optimizer`: the tracked files `.distignore` doesn't exclude, the built admin scripts (it stops when `npm run build` hasn't run), and Action Scheduler; then zips it into `build/iminify-image-optimizer.zip`, the file wordpress.org takes on submission. `composer.lock` (the development tools' versions) and `.wordpress-org` (the directory's banner, icon, screenshots and Live Preview blueprint) stay out of it.
- `php bin/check-build.php [folder]` fails when what ships holds an address but `www.iminify.com`, the licence's and the translations' support forum (`IMINIFY_BUILD_ALLOWED`; Action Scheduler's own folder is exempt), a loopback, container or reserved test host, a drive's path or a home folder (`IMINIFY_BUILD_LOCAL`, everywhere, each rule with its own case in `BuildCheckTest`), or lacks a locale's file. An address is read with or without its scheme and JSON-escaped. A new address in shipped code or text joins the list only when the plugin is meant to name it.
- `tests/Unit/VersionTest.php` holds the version to one number across the readme's Stable tag, the main file's header, `IMINIFY_VERSION` and the changelog's newest entry, which the deploy also checks against the tag. A release changes all four.
- `node tests/playground/smoke.js <built folder>` boots `.wordpress-org/blueprints/blueprint.json`, the directory's Live Preview, in WordPress Playground (`@wp-playground/cli`, which wp-env already brings) with the build mounted in place of the directory's copy, opens each screen with WordPress's debugging on, and fails on a PHP or database error, a script error, a screen that doesn't draw, or the preview reaching for Iminify. A preview must never start a real pairing with the service, so the blueprint keeps Playground's networking off and also writes a must-use plugin that answers every call to the service through `pre_http_request`: Playground's CLI ignores the networking switch, so without that plugin a Connect pressed in it reaches the live service. Keep both, and keep the test's `IMINIFY_API_BASE` on a host that never resolves.
- CI (`.github/workflows/ci.yml`) runs all of these; its `package` job builds the zip, runs the build check, Plugin Check and the Playground smoke test on the unpacked zip, and keeps the zip as the run's artifact.
- `.github/workflows/deploy.yml` releases to wordpress.org on a tag named as the version (`1.2.3`, no `v`), through 10up's deploy action with the build as trunk and `.wordpress-org` as the assets. Its build job refuses a commit CI hasn't passed on and a tag that isn't the stated version, then builds and runs the build check and Plugin Check; its deploy job, the only one given the `SVN_USERNAME` and `SVN_PASSWORD` secrets, runs no code from the repository or its packages, so no package's install script ever sees them. A failed run is run again on the same tag; a version wordpress.org already has is never tagged again.

## The development WordPress

wp-env runs WordPress in Docker: `.wp-env.json` is the development site on port 8888, `.wp-env.test.json` the test site on 8889, `.wp-env.e2e.json` the browser tests' site on 8890 and `.wp-env.multisite.json` a subdirectory multisite network on 8891 (activate the plugin there with `wp plugin activate --network`). Stop each one you started when you are done (`npm run env stop`, `npm run env:test stop`, `npm run env:e2e stop`, `npm run env:multisite stop`). `npm run test:integration:multisite` runs the integration suite on a network (`WP_MULTISITE=1`), where `NetworkTest` runs instead of skipping; CI runs both.

On Windows with Docker Desktop, run wp-env from inside WSL 2 (Node installed in the distribution, the checkout left on the Windows disk and reached at `/mnt/c/...`). wp-env then keeps WordPress's own files on the Linux file system, while from Windows every one of them is read through Docker Desktop's sharing of the Windows disk, which makes WP-CLI calls and page loads several times slower. A site belongs to the wp-env that made it, since the name of its install folder comes from the config's path, so `npm run env`, `env:test`, `env:e2e`, `env:multisite`, `test:integration` and `test:integration:multisite` all run from that side. WSL's own Node has to come first on the path: Windows' is usually on it too, and would make the sites on the Windows disk again. A script run through `wsl.exe` is not an interactive shell, so a default `~/.bashrc` returns before it reaches a Node manager's loader, which belongs in `~/.profile` for a login shell. The browser tests can stay on Windows with a Playwright installed there, with `IMINIFY_E2E_CLI` set (see `tests/e2e/support/wp.js`).

Run `npm run build` once before opening the plugin's settings page there, or `npm run start` to rebuild as you edit.

To reach a development copy of the service, a gitignored `.wp-env.override.json` (and `.wp-env.multisite.override.json` for the network) maps `dev/mu-plugins` into `wp-content/mu-plugins` and sets the constants that plugin reads (`IMINIFY_API_BASE`, `IMINIFY_DEV_RESOLVE`, `IMINIFY_DEV_CA`; its header says what each is), with a certificate file kept in the gitignored `dev/local/`. `IMINIFY_API_KEY` there connects the development site with a key. Anything about one machine stays in those two ignored places, never in a tracked file.

The checkout is mounted into every wp-env site, so a script or test that edits the plugin's source files (a mutation check, a temporary debug line) can leave a site's web server serving the edited copy from OPcache after the file is put back, while WP-CLI in the same site runs the real one. After such an edit, reload the web server in each running site's WordPress container (`apache2ctl graceful`) before trusting anything a browser or a cron request does there.
